## Concerns

### C-001: The `cc` audit cannot tell whether `pure` is enabled, and its comparison set is ambiguous
- **Where:** `build-plan.md` T-003 EARS (`cargo tree ... -i cc` clause) and the T-001 `credits` clause; `test-plan.md` Integration Tests `int_cc_build_dependency_audit` and the Intent Traceability INT-0003 AC-6 row; INT-0003 AC-6; `critique-round2.md` Resolution C-001
- **Quote:** T-003: "the crates it lists as depending on `cc` **SHALL** be exactly those with C-build `yes` in prior-art (here `blake3`), and each such row's build cell **SHALL** name its pure-Rust option (`features = ["pure"]`)" / test: "lists `blake3` (through `hash`) and nothing else that is not a `yes` row"
- **Failure mode:** plan-test-mismatch
- **Why it matters:** blake3 1.8.7 always depends on `cc` at build time: `[build-dependencies.cc]` is not optional, `pure = []` turns on nothing, and `build.rs` uses `CARGO_FEATURE_PURE` only to pick backends. So `-i cc` lists `blake3` whether or not `pure` is on, and the only `pure` check reads the prior-art text. If `"pure"` were dropped from `[workspace.dependencies]`, the build script would compile its SSE/AVX2/AVX-512 assembly through `cc` wherever a C toolchain exists, every planned check would stay green, and AC-6's "built with its pure-Rust option" would be false. Separately, `-i cc` prints the whole inverted chain (`cc`, `blake3`, `hash`, then `codec` once T-004 lands). Read literally, "exactly those with C-build `yes`" and "nothing else that is not a `yes` row" then fail on the path crates `hash` and `codec`, which have no prior-art rows, and neither text says that only direct or non-workspace dependents count.
- **Suggested response:** fix-in-plan: add a check of the resolved features to the T-003 clause and the test. For example, `cargo tree -e features -i blake3` must list `blake3 feature "pure"`, or `credits` must require that each `yes` row's named option appears in the matching root `[workspace.dependencies]` entry. Restrict the comparison to non-workspace packages, or to `cc`'s direct dependents with `--depth 1`, and update the INT-0003 AC-6 row to match.

### C-003: INT-0006 Consequences still require a format-version change for any encoding change
- **Where:** INT-0006 Consequences (first bullet), against INT-0006 Intent (staged freezing) and `build-plan.md` T-005 Notes "Freeze rule"; `critique-round2.md` Resolution C-006
- **Quote:** "Any encoding change requires a format-version change and new golden files." / INT-0006 Intent: "An encoding becomes frozen when the owner signs off the spec section that defines it (AC-6), not when a golden file is first committed."
- **Failure mode:** intent-drift
- **Why it matters:** This bullet has not changed since `620f99c`, where it matched the old Intent sentence "An encoding is frozen once a golden file pins it." After the round-2 C-006 revision, the stable chapter contradicts itself on exactly the case C-006 raised. Under its Consequences, a change the reviewer requests at the AC-6 sign-off would force a format v2 for a v1 that was never approved. The Intent paragraph and T-005's freeze rule agree with each other, so the fix is one line, but the chapter, not the plan, is the semantic authority.
- **Suggested response:** fix-in-plan: qualify the bullet, for example: "Any change to a frozen encoding (one signed off under AC-6) requires a format-version change and new golden files; before sign-off, the spec's worked example, the golden file and the encoder change together." Record the change in Transition history.

- **Where:** `build-plan.md` T-005 spec-registry EARS clause and Touches; T-003 EARS and Notes; `test-plan.md` T-003 `only_registered_alg_ids_decode`; `critique-round2.md` Resolution C-011

### C-005: Oversize length and count prefixes are still tested only at offset 0
- **Where:** `build-plan.md` T-004 oversize-prefix EARS clause; `test-plan.md` T-004 `oversize_prefixes_rejected_without_allocation`; `critique-round2.md` Resolution C-013
- **Quote:** "the `u64::MAX` varint as a `Bytes` and `String` length and as a `Vec`, `BTreeSet` and `BTreeMap` count, followed by three bytes → `UnexpectedEnd { at: 0 }`, no panic."
- **Failure mode:** plan-test-mismatch
- **Why it matters:** The resolution says "Invalid values are embedded at offset 2". That holds for the varint, bool, option and UTF-8 tests but not for these five prefix decoders. At offset 0, the absolute and the value-relative offset are the same number, so the clause's "at the prefix's offset" is still unchecked for these decoders, which is the gap round-2 C-013 described. A relative or hard-coded offset in the prefix path's `UnexpectedEnd` branch would pass every planned test.
- **Suggested response:** fix-in-plan: embed each oversize prefix as the second element of a `Vec` whose first element is one byte (`Vec<Bytes>`, `Vec<String>`, `Vec<Vec<u64>>`, `Vec<BTreeSet<u64>>`, `Vec<BTreeMap<u64, u64>>`) and expect `UnexpectedEnd { at: 2 }`.

### C-006: AC-10 and T-008 require the README to say that `cargo deny check` takes no flags
- **Where:** INT-0003 AC-10, against INT-0003 Intent, AC-9 and INT-0022 Intent; `build-plan.md` T-008 README clause; `test-plan.md` `readme_keeps_statement_and_links_book`; `critique-round2.md` Resolution C-016

- **Failure mode:** intent-drift
- **Why it matters:** INT-0003's Intent and AC-9, and INT-0022's "The project's own tooling follows the same rule", make only the three project commands flagless. On the host, `cargo deny check --help` (cargo-deny 0.20.2) lists `[WHICH]...` plus `-g/--graph`, `-s/--show-stats`, `-W`, `-A`, `-D` and `--feature-depth`. The new criterion and its test therefore require a false sentence in the README, and they extend the owner's rule to a third-party tool without recording it. "A statement" also gives the test no fixed phrase to look for.
- **Suggested response:** fix-in-plan: reword AC-10 (amending its existing Transition-history note) and the T-008 clause. The README documents all four commands and states that `cargo ci`, `cargo policy` and `cargo book` take no flags, while `cargo deny check` is run exactly as shown. Pin the exact sentence that `readme_keeps_statement_and_links_book` checks for.

### C-008: The narrowed `names` clause lets a publishable package skip the naming rule
- **Where:** `build-plan.md` T-001 `names` clause and Notes; INT-0003 Intent (Boundaries) and AC-8; `test-plan.md` `policy_requires_single_word_names`; `critique-round2.md` C-018 and its Resolution
- **Quote:** "**WHEN** an unpublished workspace package's name does not match `[a-z][a-z0-9]*`, **THEN** policy **SHALL** fail with rule `names` and name the package."
- **Failure mode:** intent-drift
- **Why it matters:** Round-2 C-018 said T-001's rule "can stay as written for Sprint 0". The clause was narrowed anyway (at `620f99c` it read "a workspace package name"), and no rule checks INT-0003's boundary "Workspace crates are `publish = false`". Cargo applies `[workspace.package] publish = false` only to members that declare `publish.workspace = true`, so a member that leaves the line out is publishable and skips `names` without any failure. If no member declares it, `names` checks nothing and `policy_passes_on_workspace` passes without checking a single name, and `policy_requires_single_word_names` has no publishable case.
- **Suggested response:** fix-in-plan: keep `names` over every workspace package for Sprint 0. Alternatively, have policy fail when any member does not resolve to `publish = false`, until INT-0003 records a publishable crate. Add that case to `policy_requires_single_word_names`.

### C-009: No test runs `cargo book` without arguments or `cargo policy` through its alias, and the idempotence clause covers only `cargo ci`
- **Where:** `build-plan.md` T-006 first EARS clause and Notes, T-007 idempotence clause and Notes; `test-plan.md` Intent Traceability INT-0002 AC-2 and INT-0003 AC-9 rows, `cli_exit_codes`, `int_tooling_is_idempotent`
- **Quote:** T-006: "**WHEN** `cargo book` runs at the repository root with no arguments, **THEN** it **SHALL** check `docs/`" / T-007: "**WHEN** `cargo ci` runs twice in a row on a clean checkout" / test: "`cargo ci`, `cargo policy` and `cargo book` twice each → `git status --porcelain` empty after every run."
- **Failure mode:** plan-test-mismatch
- **Why it matters:** T-006's no-argument clause maps to `book_intents_pass_strict`, which is a library test, and to the `cargo ci` step `book`, which "runs in-process through the `book` library". `cli_exit_codes` has no no-argument case. `int_tooling_is_idempotent` is the only test that runs `cargo book` without arguments or `cargo policy` through its alias, and it asserts only `git status`. A wrong default directory (exit 2) or a broken `policy` alias would therefore pass every test, even though the README documents both commands (AC-10). In the other direction, the `cargo policy` and `cargo book` runs in `int_tooling_is_idempotent` trace to no clause: T-007's idempotence clause names only `cargo ci`, yet the AC-9 row credits "T-007 / two runs leave the tree clean" for all three commands.
- **Suggested response:** fix-in-plan: extend T-007's idempotence clause to `cargo ci`, `cargo policy` and `cargo book`, or add idempotence clauses to T-001 and T-006. Make `int_tooling_is_idempotent` assert exit 0 on every run and, for `cargo book`, one counted line per chapter. Alternatively, add a no-argument case to `cli_exit_codes` that runs the binary with `Command::current_dir` set to the repository root (not `set_current_dir`, so parallel tests stay safe).

### C-010: T-006's refusal of an unknown declaration value and of a directory without a marker exists only in sprint prose
- **Where:** INT-0002 Intent (Declaration paragraph) and Transition history; `build-plan.md` T-006 declaration EARS clause; `test-plan.md` `unsupported_declaration_is_an_error`, `missing_marker_is_an_error`; `critique-round1.md` Resolution C-003 and `critique-round2.md` Resolution C-005
- **Quote:** INT-0002: "a Book opts into this contract with the line `typed-acceptance: 1` in its `docs/.sprint-loop-book` marker. - **Why it matters:** INT-0002 calls itself "the normative definition of that grammar", and it defines only declared (`typed-acceptance: 1`) and undeclared Books. That observable rule, which AC-5 asks Sprint Loops to adopt, was decided in the round-1 C-003 and round-2 C-005 resolutions and does not appear in INT-0002 or its Transition history. The missing-marker half follows from Sprint Loops defining a Book by its marker and is lower risk, but it belongs in the same amendment.
- **Suggested response:** fix-in-plan: amend INT-0002's Declaration paragraph, with a Transition-history entry. It should say that an unknown `typed-acceptance` value is refused rather than read with the port rule, and that a directory without a `.sprint-loop-book` marker is not a Book. T-006 can then stay as written.
